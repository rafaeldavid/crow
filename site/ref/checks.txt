# Crow reference: writing checks

How to write the deterministic checks a buyer binds, for a CSV, a JSON report and recorded data.

## Writing checks that protect a buyer

On a checks-only deal the checks are the whole deal. Write each as if the seller will deliver the least that passes. The checks and the judges read the delivered file only: a file the delivery only links to is not fetched or checked, so put what you need in the delivery. A CSV once passed every check its buyer wrote with emails like `a@a`, one date repeated, and an instruction string as a customer ID. These checks would have refused it:

```json
[
  { "id": "cols", "type": "csv_columns_exact", "required": true, "columns": ["customer_id", "email", "signup_date"] },
  { "id": "rows", "type": "row_count_range", "required": true, "min": 3, "max": 1000 },
  { "id": "uniq-id", "type": "unique_key", "required": true, "columns": ["customer_id"] },
  { "id": "uniq-email", "type": "unique_key", "required": true, "columns": ["email"] },
  { "id": "id-format", "type": "regex_match_rate_min", "required": true, "column": "customer_id", "pattern": "^C[0-9]{6}$", "minBps": 10000 },
  { "id": "email-format", "type": "regex_match_rate_min", "required": true, "column": "email", "pattern": "^[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(\\.[A-Za-z0-9-]+)*\\.[A-Za-z]{2,}$", "minBps": 10000 },
  { "id": "date-format", "type": "iso8601_date_column", "required": true, "column": "signup_date" },
  { "id": "date-range", "type": "regex_match_rate_min", "required": true, "column": "signup_date", "pattern": "^2026-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])$", "minBps": 10000 },
  { "id": "hidden", "type": "hidden_characters_max", "required": true, "max": { "total": 0 } }
]
```

- Put `unique_key` on every column that should not repeat, not only the key.
- There is no numeric range check: write a range as a pattern.
- Column patterns are full matches; an empty cell does not match. Limits: "Pattern and work limits", below.
- `minBps` and `maxBps` are basis points: 10000 is 100%.
- Checks cannot say that values are plausible or real.

The check types: `csv_columns_exact` (`columns`), `row_count_range` (`min`, `max`, counting data rows; the header line does not count), `unique_key` (`columns`), `null_rate_max` (`column`, `maxBps`), `regex_match_rate_min` (`column`, `pattern`, `minBps`), `iso8601_date_column` (`column`), `json_schema` (`schema`), `hidden_characters_max` (`max` per class: `tag`, `bidi`, `variationSelector`, `otherIgnorable`, `total`), `reference_row_match_min` (`reference`, `keyColumn`, `minBps`), `signature_valid` (`alg`, `publicKey`, `message`, `signature`), `passes_through` (`series`, `waypoints`, `tolerance`), `monotonic_column` (`series`, optional `minStep`, `maxStep`), `equal_lengths` (`series`). Each takes an `id` and `required`; a failed required check refunds the buyer. A failed check's line is in the judgment record, `deterministic[].detail` (`GET /v1/commitments/<id>/judgment`).

- **Before you sign,** read `checkKinds` on all three named adjudicators (`GET /v1/adjudicators/<address>`); a record with no list runs none of `signature_valid`, `passes_through`, `monotonic_column`, `equal_lengths`. An adjudicator that lacks a kind your terms name, required or optional, declines the offer as primary and signs no decision in a later turn: the deal runs to the next adjudicator or its default outcome, which returns the price and the fee.

- **`unique_key` with several columns** treats them together as one key: `"columns": ["t_ms", "joint"]` fails only when a row repeats the same pair, so `t_ms` may repeat across joints. For columns that must each be unique, write one `unique_key` per column.
- **`hidden_characters_max`** counts these code points in the delivered text, before any normalization, and fails when a class's count is over its `max`; name at least one class, and `total` bounds their sum. `tag`: U+E0000 to U+E007F. `bidi`: U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069. `variationSelector`: U+FE00 to U+FE0F, U+E0100 to U+E01EF, U+180B to U+180D, U+180F. `otherIgnorable` (zero-width and other invisible characters): U+00AD, U+034F, U+115F, U+1160, U+17B4, U+17B5, U+180E, U+200B to U+200D, U+2060 to U+2064, U+206A to U+206F, U+3164, U+FEFF, U+FFA0, U+1D173 to U+1D17A. `"max": {"total": 0}` fails on any of them.
- **`reference_row_match_min`** compares the delivery with a file you hold, in the delivery's format: it passes when at least `minBps` of the reference file's rows appear in the delivery, matched on `keyColumn`, with the same value in every column the reference has. Upload the file before the offer with `POST /v1/ciphertext` (`ref/http-seller.txt`, "Encrypt and deliver", shows the call) and put the answer's `uri` and `id` in `"reference": {"uri": "<uri>", "sha256": "<id>"}`. The operator stores the file in the clear, and anyone with its hash can read it, so put nothing in it you would not publish. Upload it to the store the terms' adjudicators read, as for a delivery: each declines the offer when its store cannot return the file. It is at most `limits.maxCiphertextBytes` in discovery (1,048,576 bytes on these nodes), and a reference with Unicode tag characters fails the check. A pass shows the rows are present, not that the seller produced them. The rest: https://github.com/rafaeldavid/crow/blob/main/docs/api.md, "Reference files".

For a report delivered as one JSON document, "Writing checks for a report" below lists the `json_schema` subset and four recipes.

## Pattern and work limits

- A pattern (`regex_match_rate_min`, or `pattern` in `json_schema`) takes no backreferences, lookarounds, named groups, flags, `\b`, `\p{...}`, `\u` or `\x`; `^` anchors only as the first character, `$` only as the last.
- Limits: 200 characters; repeat counts up to 1,000; compiled, 5,000 states and 50,000 compile steps; one `json_schema` check's patterns, 20,000 states together.
- No pattern reads a string over 10,000 code points. A `json_schema` check whose `pattern` meets a longer one fails (`a pattern met a string over 10000 code points`), also under `not`, `anyOf` and `oneOf`, even where another branch would pass. For an `anyOf` where one branch takes long strings, put `"maxLength": 10000` beside the other branch's `pattern`: that branch then fails on length and its pattern is not read. In `regex_match_rate_min` a longer cell counts as not matching.
%% T-612: the nesting cap on JSON-table cells goes here, as one bullet, once its pull request merges; read the number from the code.
- All checks on one delivery share 50,000,000 work units; there is no timer. Matching costs, per code point read, 1 unit, plus 1 per live state and 1 per branch followed. Reading cells, names and text costs units too.
- A check that runs out is inconclusive (`inconclusive: the check work budget for this delivery ran out`): the deal escalates, even if that check is optional, unless another required check failed (reject). Expect the appeal adjudicator, with the same checks and budget, to sign nothing; the default outcome then returns the price and the fee to the buyer.
- The terms schema accepts some checks the engine refuses: a pattern over a compile limit, a `json_schema` over a limit or outside the subset, a waypoint with the wrong number of coordinates, `minStep` above `maxStep`. No operator or adjudicator refuses them at the offer, and each fails every delivery (`check invalid: <reason>`). In a clone, after `pnpm install && pnpm build`, `node examples/check-terms.ts terms.json` warns of each.

## Writing checks for a report

A report delivered as one JSON document (`deliverable.kind` `document`, `format` `application/json`) is checked with `json_schema`. The check walks a subset of JSON Schema as data. It refuses a schema that uses any keyword outside the subset, and the check then fails, so write only these.

Supported keywords: `type`, `enum`, `const`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `uniqueItems`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minLength`, `maxLength`, `pattern`, `anyOf`, `allOf`, `oneOf`, `not`.

Ignored annotations: `$schema`, `title`, `description`, `$comment`, `examples`, `default`.

Not supported: `contains`, `if`, `then`, `else`, `$ref`, `$defs`, `format`, `patternProperties`, `prefixItems`, `propertyNames`, `multipleOf`, `dependentRequired`.

- `properties` checks a property only when it is present: name it in `required` too.
- `pattern` matches anywhere in the string unless you anchor it with `^` and `$`. A leading `^` binds only the first top-level `|` alternative, a trailing `$` only the last.
- A schema holds at most 2,000 subschemas, nested at most 32 deep.

Four recipes for an audit report with a `commit`, a `filesReviewed` list and a `findings` list. Each finding has a `locations` list: a location names a `file` and may add `lines` and an `excerpt`.

**Pin a commit.** `const` holds the report to the commit the terms name.

```json
{ "id": "commit", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["commit"], "properties": { "commit": { "const": "7c1e4b9a2d3f5068a1b2c3d4e5f60718293a4b5c" } } } }
```

**Hold every location to the scope.** A finding names one location or several. `items` applies the rule to each one, so a finding with one file outside the agreed scope fails. `minItems` 1 refuses a finding that names no place in the code.

```json
{ "id": "locations", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["findings"], "properties": { "findings": { "type": "array", "items": {
  "type": "object",
  "required": ["locations"],
  "properties": { "locations": { "type": "array", "minItems": 1, "items": {
    "type": "object",
    "required": ["file"],
    "properties": { "file": { "enum": ["contracts/Vault.sol", "contracts/InterestModel.sol", "contracts/PriceFeed.sol"] } }
  } } }
} } } } }
```

**Require proof by severity.** The proof term is the deal's to set: say in the description which severities need proof-of-concept files, and hold it with this check. There is no `if`, so say it with `anyOf`: a finding is Low or Info, or it carries proof-of-concept files. That is proof for Medium or higher. To require proof from High up, add `"Medium"` to the list of severities that need none. To require no proof, leave the check out.

```json
{ "id": "proof", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["findings"], "properties": { "findings": { "type": "array", "items": {
  "type": "object",
  "required": ["severity"],
  "properties": { "severity": { "enum": ["Critical", "High", "Medium", "Low", "Info"] }, "pocFiles": { "type": "array", "minItems": 1 } },
  "anyOf": [ { "properties": { "severity": { "enum": ["Low", "Info"] } } }, { "required": ["pocFiles"] } ]
} } } } }
```

**Match a file list in any order.** Three distinct entries, each from the agreed scope, are the scope itself. Set `minItems` and `maxItems` to the number of files in scope.

```json
{ "id": "coverage", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["filesReviewed"], "properties": { "filesReviewed": {
  "type": "array", "uniqueItems": true, "minItems": 3, "maxItems": 3,
  "items": { "enum": ["contracts/Vault.sol", "contracts/InterestModel.sol", "contracts/PriceFeed.sol"] }
} } } }
```

- A report with no findings passes all four. Add `"minItems": 1` to `findings` only if an empty report is not acceptable work.
- Require only what every report of this kind has. In the worked example a location's `lines` and `excerpt`, a finding's `impact` and `status`, and the report's `summary`, `reportDate` and `salt` are optional: the schema names them in `properties` and leaves them out of `required`. A buyer who needs one of them adds it to `required` before agreeing.
- The subset cannot compare two fields (a line range that ends before it starts), cannot require one property to be unique across a list (two findings with the same id), and cannot say that a finding is true.
- For what the checks cannot say, add a rubric. Judges read a report of up to 100,000 characters whole. They read a longer report as a sample of its lines, and a sampled read escalates the deal to the appeal adjudicator. The checks always run on the whole report.

A complete commitment with these checks, the full report schema and an optional five-criterion rubric is `spec/examples/commitment.audit-report.example.json` in [the repository](https://github.com/rafaeldavid/crow/blob/main/spec/examples/commitment.audit-report.example.json).

## Checking a signature

`signature_valid` passes when the exact bytes at one place in a JSON delivery carry a valid signature by the key whose fingerprint the terms pin. It proves that the key's holder signed those bytes, and nothing more: not that the bytes are true, and not that the key sits in a device. The delivery must be a JSON document. Every parameter is a string.

```json
{ "id": "manifest-signature", "type": "signature_valid", "required": true, "alg": "ecdsa-p256-sha256",
  "publicKey": { "pointer": "/pubkey_pem", "format": "spki-pem", "spkiSha256": "sha256:<64 hex>" },
  "message": { "pointer": "/manifest_text", "encoding": "utf8", "jsonEquals": "/manifest" },
  "signature": { "pointer": "/manifest_sig", "encoding": "base64", "format": "der" } }
```

- **Algorithms,** a closed list: `ecdsa-p256-sha256` (signature `der`, read strictly, or `raw`, r then s; a high s passes) and `ed25519` (`raw` only; strict RFC 8032, not ZIP 215). `signature.encoding` is `base64`.
- **The key** travels in the delivery. `publicKey.format` `spki-pem`: one PEM block labelled `PUBLIC KEY`, LF or CRLF, an optional final line end, nothing else. `spki-base64`: plain base64 of the DER `SubjectPublicKeyInfo`. A P-256 point must be uncompressed. `spkiSha256` pins the SHA-256 of the DER, which `openssl pkey -pubin -outform DER | sha256sum` prints. A different key fails the check before any signature work.
- **The signed bytes are exact.** Nothing is canonicalised. `message.pointer` names a string: with `utf8` the signed bytes are its UTF-8 encoding (a lone surrogate fails), with `base64` they are the decoded string. Decimals in the signed text are fine.
- **`jsonEquals` ties the signed text to an object.** The signed bytes must parse as JSON to the value at the pointer it names, so your `json_schema` checks read fields the key signed. Without it, nothing says the object and the signed text agree. Numbers compare as the same 64-bit double, so `1.0` equals `1`, and digits past double precision are not bound: keep a nonce or an ID as a string. A key repeated in the signed text counts with its last value, as `JSON.parse` reads it.
- **Base64 has one spelling:** standard alphabet, padding required, no whitespace, no non-zero trailing bits.
- **Limits:** the key string at most 1,024 characters, the signature string at most 256 (DER at most 72 bytes, raw exactly 64), an RFC 6901 pointer at most 512; the message has only the delivery's limit. Work units ("Pattern and work limits"): 200,000 per verification, 1 per message byte (about 2 with `base64`), 1 per value `jsonEquals` compares.
- **Failure lines,** the first failing step only, never quoting the delivery. In order: `not a JSON document`; for `publicKey`, `message`, `signature` in turn, `<name>: nothing at the pointer`, `<name>: not a string`, and `publicKey: too long` or `signature: too long`; `publicKey: not a PEM public key` or `publicKey: not valid base64`; `publicKey: fingerprint differs from the terms`; `publicKey: not a P-256 key` or `publicKey: not an Ed25519 key`; `signature: not valid base64`; `signature: wrong length`; `message: not well-formed text` or `message: not valid base64`; `signature: not valid DER`; `signature does not verify`; `message: not JSON`; `message: differs from the value at jsonEquals`.
- **Not proved:** that the signed data are true, that the key sits in a device, or that the run is new (hold the order's nonce, in a signed field, with a `json_schema` `const`). No kind hashes a field: a hash in the signed text does not tie the data it names.
- **Test vectors** (Python-signed documents, their checks and exact failure lines): https://github.com/rafaeldavid/crow/tree/main/spec/test-vectors/signature-valid. In a clone, after `pnpm install`, `node spec/test-vectors/signature-valid/verify.mjs --check check.json delivery.json` runs one document against one check, without the work budget. Python's `cryptography` accepts the vector `ed25519/small-order-key`; this check refuses it.

## Checking recorded data

`equal_lengths`, `monotonic_column` and `passes_through` check a recording's series:

```json
[
  { "id": "lengths", "type": "equal_lengths", "required": true,
    "series": [ { "pointer": "/telemetry/t_ms" }, { "pointer": "/telemetry/q1_mdeg" }, { "pointer": "/telemetry/q2_mdeg" } ] },
  { "id": "time", "type": "monotonic_column", "required": true,
    "series": { "pointer": "/telemetry/t_ms" }, "minStep": 1, "maxStep": 16 },
  { "id": "waypoints", "type": "passes_through", "required": true,
    "series": [ { "pointer": "/telemetry/q1_mdeg" }, { "pointer": "/telemetry/q2_mdeg" } ],
    "waypoints": [ [10000, -45000], [30000, -20000] ], "tolerance": 500 }
]
```

- **A series** is `{"pointer": "..."}`, the array at that RFC 6901 pointer (at most 512 characters) in a JSON delivery, or `{"column": "..."}` (name at most 128 characters), a column of a CSV or of a JSON array of flat objects with the same keys.
- **Integers only,** in the data and the check, within +/-(2^53 - 1). Nothing is rounded: record fixed units (ms, millidegrees). A pointer's entries are JSON numbers as `JSON.parse` reads them (`1.0` is 1, `1e2` is 100, `"1"` fails); so is a number cell in a JSON array of objects. A CSV or string cell is `0`, or digits with an optional `-` and no leading zero, at most 16 digits: no `+`, space, exponent, `-0` or empty cell.
- **`equal_lengths`:** `series`, 2 to 32, `pointer` only. Passes when every pointer is an array of one length. It reads no entry.
- **`monotonic_column`:** one `series`; optional integers `minStep` (default 0) and `maxStep` (default none), 0 or more, `minStep` <= `maxStep`. Passes when no row is lower than the row before and each step is within them. `minStep` 1: strictly increasing. `minStep` = `maxStep`: a fixed step. 0 or 1 rows pass: set the count with `json_schema` `minItems`, or `row_count_range` on a table. No decreasing form.
- **`passes_through`:** `series`, 1 to 32, one per axis; `waypoints`, 1 to 1,024, each one integer per series in that order; integer `tolerance`, 0 or more. Passes when rows r1 < r2 < ... exist so that at row rk every series is within `tolerance` of waypoint k (absolute difference, per axis). Each waypoint needs its own later row, so two equal waypoints need two. All series need the same number of rows.
- **Failure lines** (N is the series, R the row, from 1; none quotes a value; `monotonic_column` writes `series:` without N):
  - reading: `not a JSON document`, `series N: nothing at the pointer`, `series N: not an array`, `series N: column not found`, `series N: the column name appears twice`, `series N: row R is not an integer`; an unreadable table gives its reason, such as `JSON deliverable is not an array of objects` or `CSV: ...`;
  - `passes_through`: `series N has X rows; series 1 has Y`; `reached K of M waypoints in order; waypoint W is not within tolerance after row R` (or `... in any row`);
  - `monotonic_column`: `row R is lower than row Q`, `row R steps less than minStep after row Q`, `row R steps more than maxStep after row Q` (Q is the row before R);
  - `equal_lengths`: `series N has X entries; series 1 has Y`.
- **Work units:** 1 per series, plus 1 per 16 characters of its pointer or 1 per header column; 1 per entry read; 1 per coordinate or step compared.
- **Tie the series to a key:** add `signature_valid` with `message.jsonEquals` naming an object that holds every series these checks read (here `/telemetry`). Otherwise nothing says a key signed them.
- **The buyer's order:** waypoints are fixed in the terms, so the buyer picks them before the offer.
- **Not proved,** even signed: that the recording is real (a seller can compute or edit series that pass all three); physical consistency, such as speed against position; the path between samples (bound gaps with `maxStep` on time); one distance across axes (`tolerance` is per axis).

## Writing checks for a robot episode

A robot run sold as one JSON document is checked with `json_schema` too. The sell command's `--sample robot-episode` sells one arm episode in Hugging Face's LeRobot v3 layout: `meta.info` holds `meta/info.json` field for field, `data` holds the frame table one array per column, and `provenance` holds the arm's serial hash, the order's nonce and waypoints, the measured pose at each waypoint, the recording's hash and a device signature. Its ten checks are in `examples/robot-episode.ts`.

- **Bounds are whole numbers.** The terms are hashed and signed, so every bound in a check is an integer. The data need not be: keep joint values in degrees with decimals, as the controller reports them, and the arm's limits are whole numbers in degrees (-360 to 360 for a joint position, 223 degrees per second for a joint speed).
- **One bound per vector.** The subset has no `prefixItems`, so `items` holds all six values of a joint vector to one bound. Use the widest joint's limit; a joint with a tighter limit is not held to it.
- **List every section.** `additionalProperties: false` at the top refuses any section it does not name: list `data` and `provenance` as well as `meta`.
- **Freshness comes from the order.** A `const` on the nonce and the waypoints, and a `minimum` and `maximum` within 1 degree of each waypoint, hold the delivery to a run made after the order, when the buyer draws them. The sample's seller draws its own, because the test buyer issues no orders yet. `signature_valid` verifies the signature ("Checking a signature", above); a `json_schema` check alone only pins the signed message's format.
- **Integer series.** `passes_through` and `monotonic_column` do not read the sample's six-value joint vectors: for them, record one integer array per axis ("Checking recorded data", above).

```json
{ "id": "joint-positions", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["data"], "properties": { "data": { "type": "object", "required": ["observation.state"], "properties": { "observation.state": {
  "type": "array", "minItems": 1000, "maxItems": 1875,
  "items": { "type": "array", "minItems": 6, "maxItems": 6, "items": { "type": "number", "minimum": -360, "maximum": 360 } }
} } } } } }
```

## Writing checks for a telemetry run

A robot run's readings sold as one CSV file, one row per sample, take the column checks. The template is `fixtures/terms/telemetry-run.yaml` in [the repository](https://github.com/rafaeldavid/crow/blob/main/fixtures/terms/telemetry-run.yaml): a run ID on every row, a timestamp in ms, and integer readings in fixed units, each held to its range by a pattern.

- **Duration, rate and gaps by counting.** A `regex_match_rate_min` check on the timestamp column with `minBps: 10000` allows only the grid's timestamps, written without leading zeros. `unique_key` forbids a repeat, and `row_count_range` with `min` and `max` both at the grid's size then makes each timestamp appear once: the whole run at the agreed rate, with no gap. With a `minBps` below 10000 the count proves nothing.
- **Order and step in one check:** `monotonic_column` on `{"column": "t_ms"}` with `minStep` = `maxStep` = the period; it does not set the first value or the row count. No check compares one column's values with another's.

## The buyer's own check run

Step 9 of https://crow.direct/buy.txt sends you here; this run is optional. In a clone of the repository after `pnpm install && pnpm build`, save the work with the agreed format's extension, such as `work.json`, save the terms as `terms.json` (`curl -s $OP1/v1/commitments/<id>/terms`) and run `node examples/check-delivery.ts terms.json work.json`. Exit 0 means the checks accept it, or on a rubric deal do not refuse it.
