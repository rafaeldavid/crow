# CI review, 2026-11-18 (T-504, roadmap row N173)

## Summary

A code change on the chain side waits a median 12 min 32 s for `check` on its pull request (p90 23 min 50 s). Its merge then starts a run on main that waits a median 32 min 25 s. Three jobs set those waits, and none of them needs to run on most changes:

- The model check (`formal (TLC)`) reads only `formal/`. Its liveness configs take a median 25 min 24 s on every push to main, and 97 of 98 pushes did not touch `formal/`.
- `forge test` reads only `contracts/` and `fixtures/beacon/`. It is the last job to finish on 104 of 112 chain-side pull-request runs, and 112 of 201 pull-request runs touched neither.
- A merged docs or task-file pull request starts a full run on main: 38 of 98 pushes, 2,755.7 runner minutes in 3.8 days.

This review landed the approved changes: the signer's chain test in CI, and crow-private's tests on every push with their failing test fixed. It also landed the script that measures all of this. Five more workflow changes wait as unmerged pull requests for Rafa, each with its measured saving. Two of them cut a push to main from 32 min 25 s to about 12 min 53 s, and a chain-side pull request's median wait by about 5 min. Three example tests passed only on a rerun in the last 4 days. Two were already fixed on main by later commits; the third, the refund test, was fixed the same day (T-508, PR 633).

## Scope

- **Repositories:** `rafaeldavid/holdback` (GitHub Actions: `ci`, `id-check`, `walkthrough`, CodeQL's default setup, Dependabot) and `rafaeldavid/crow-private` (its tests).
- **Data:** every completed run, every job of every attempt, and every pull request, read from GitHub on 2026-11-18 (read only). Holdback's CI started on 2026-10-30, so the 30-day window holds 19 days of runs.
- **Two windows:**
  - The **current layout**, 2026-11-14 11:00 to 2026-11-18 06:00 UTC (3.8 days): `ci.yml` last changed its jobs at 2026-11-14 10:40 UTC (T-410), so these numbers describe CI as it is. The baseline and every saving below use this window.
  - The **30 days**, 2026-10-19 to 2026-11-18 06:00 UTC: volumes, reruns and flakes, across earlier layouts.
- **Kinds of change** come from each pull request's file list (`kindOf` in the script): `tasks` (only `docs/tasks/`), `docs` (what `ci.yml`'s changes job calls docs), `site`, `code`, `code-chain` (a file the chain pattern names, so the contracts and anvil jobs run), `contracts` and `ci` (`.github/`).
- **Wall time** runs from the run's creation (the push) to its `check` job's end, first attempt.
- **Not measured:** the tokens a session spends while it waits on CI. The wait is measured in minutes; tokens per change come from the session transcripts, which this script does not read.
- **Reproduce:**

  ```bash
  node scripts/metrics/ci-runs.mjs --cache reports/scratch/ci-cache.json --since 2026-11-14T11:00:00Z --until 2026-11-18T06:00:00Z --md reports/scratch/ci-runs-current.md
  ```

  A second run reads only the new runs. `--offline` reads the cache alone, and `tests/metrics/ci-runs.test.ts` checks every number on a fixture.

### The other questions

- **A docs-only fast path.** A one-line Status change already passes `check` in a median 12 s to 13 s, after `changes`, `check`, `gitleaks` and `id-check`. It needs `gitleaks`, since a secret can land in a doc, and `id-check`. The waste is its merge: a full run on main (PR 628).
  - The fast path skips the test shards, and some shard tests read docs: `tests/cut-feature-alignment.test.ts` scans every tracked file, and the decisions-status, design-map, id-check and site-guides tests read `docs/`. So a docs pull request can merge with one of them failing.
  - Main's push catches it today, and PR 628 keeps the shards on a docs-only push for that reason.
  - Running those few test files on docs pull requests would catch it before the merge. That is a workflow change and not proposed here.
- **A merge queue or batching.** GitHub's merge queue serves repositories owned by an organization; `rafaeldavid/holdback` is a personal account's repository (inferred from GitHub's documentation). Batching docs is already the coordinator's practice. With PR 628, a docs merge costs about 4 minutes, so batching docs would save little more.
- **Caching.**
  - The pnpm store and the TLA+ tools are cached already.
  - Foundry's toolchain step and the submodules take seconds (contracts job setup, median 12 s).
  - The one cache worth adding is the compile output on push (PR 629).
  - Building once and sharing the build would save about 20 s in each of 7 jobs, but an artifact's upload and download cost about as much (inferred). Not proposed.
- **Shard balance.** The four shards' medians lie within 46 s (2 min 22 s to 3 min 08 s). They are not on the chain side's critical path. No change.
- **The walkthrough.** It runs only on changes to the site, the examples, the packages or the operators, and takes a median 1 min 34 s. It needs the network, so it stays outside `check`. No change, apart from cancelling overtaken runs (PR 626).
- **CodeQL.** The default setup ran 290 times in the window (191 pull requests, 99 pushes), 939.4 runner minutes, at a median 2 min 58 s. It is not required. Moving it is a repository setting, Rafa's. Advanced setup with `paths-ignore: docs/**` and a daily run on main in place of every push would save a few hundred runner minutes a window (inferred). Low priority.
- **PR 616** (`actions/setup-java` 6.2.0 to 6.3.0). Its release was published on 2026-11-14 at 04:53 UTC, 4 days before this review, so it is inside the 14-day release-age wait until 2026-11-28. Its failed run of 2026-11-17 failed on two repository-wide tests that read main's state at the time, not on the bump. Its `id-check` fails because Dependabot names no task. PR 630 makes Dependabot wait 14 days for every action.

## The report's evidence, by practice

Read in full, in parts, on 2026-11-18, from `https://vincent.build/openclaw-ci-cost-reduction/`. The author's measurements are of OpenClaw's CI on sponsored Blacksmith runners.

- **Headline:** runner-hours fell 86.5% (158,546 to 21,395 a week) and jobs 79.7% between a September peak week and a November week. The author credits no single fix, and notes the workload changed too.
1. **Waste tests:** a per-test audit (name the behaviour, show a believable bug that fails it, keep one strong owner). Test files fell by 417,906 lines while the code grew. No CI time is attributed to it.
2. **Right stage:** three tiers (pull request, push to main, scheduled). CodeQL on main moved to an hourly schedule that reuses an unchanged result for up to 24 hours. A 90-second admission delay lets a newer push cancel a run before it takes a runner. No durations are given.
3. **Repeat reviews:** one automatic review per pull request; follow-ups by request. No percentage is claimed.
4. **Test what changed:** a deterministic planner maps the diff to test files and widens on any doubt. Three runs dropped from about 4,000 to 7,000 test entries to 15 to 97. The author says smaller green runs alone do not prove coverage.
5. **Faster local tools:** a typecheck went from 447 s to 64 s locally. The author excludes it from the headline.
6. **Environment:** blobless checkouts; trusted writers separated from restore-only jobs. Turning off test isolation in selected lanes saved 44.3% in those lanes.
7. **Runners:** packing 95 shards into 63; balancing cut the slowest job from 403 s to 300 s. A 16-core runner was 41.7% cheaper and 16.5% slower than a 32-core one.

The report names no merge queue, no docs-only fast path and no concurrency group. It treats a flaky test as one to repair, not to retry.
